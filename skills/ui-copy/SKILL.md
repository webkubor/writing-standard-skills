# 界面文案

## 适用范围

适用于 Web、桌面、移动端和插件界面里的按钮、标题、空态、错误、提示、卡片、表单标签和确认文案。它管用户看到什么、下一步做什么；字号、颜色、间距、分页和响应式布局由设计或渲染规范负责。

## 五个原则

1 **先给状态，再给动作**：用户先知道发生了什么，再知道点哪里。
2 **按钮写动作结果**：写“保存更改”，不写“提交”；写“重试加载”，不写“确定”。
3 **错误可恢复**：写失败点、影响和下一步，不把错误码当全部说明。
4 **空态给出口**：没有数据时给创建、导入、筛选或文档入口，不只写“暂无数据”。
5 **短句具体**：避免套话、夸张承诺和无信息量的感叹。

## 六类文案

### 按钮

| 场景 | ❌ 反例 | ✅ 正例 |
|---|---|---|
| 保存表单 | 提交 | 保存更改 |
| 删除确认 | 确定 | 删除 3 个项目 |
| 失败重试 | 确定 | 重试加载 |
| 导出 | 开始 | 导出 CSV |

按钮文字要能预测点击结果。破坏性动作在按钮上写对象和数量，确认框再解释不可逆影响。

### 标题

标题说明当前对象或任务，不写口号：

```text
❌ 项目管理
✅ 项目列表

❌ 让工作更高效
✅ 导入团队项目
```

### 空态

```text
还没有项目
导入已有项目，或创建第一个项目。
[创建项目] [导入项目]
```

空态要区分“没有数据”“筛选无结果”“权限不足”“加载失败”。这四种状态不能共用一句“暂无数据”。

### 错误

```text
项目列表加载失败
网络请求超时，刚才的筛选条件没有改变。
[重试加载]
```

错误文案写用户能理解的事实和下一步；原始错误码可以放在“详情”或日志入口，不占据主提示。技术细节不能替用户判断影响。

### 超长文本

- 标题优先保留对象名和动作，不硬塞完整描述。
- 列表、按钮和标签优先显示关键字段，完整值放详情或可访问的展开区域。
- 截断不能改变语义；截断后仍需可读、可复制或可展开。
- 多语言和动态内容要为最长文本预留空间，不用固定短句掩盖溢出。

### 卡片文案

卡片按“对象 → 状态 → 下一步”组织：

```text
项目 A
部署完成 · 2 分钟前
[查看结果]
```

卡片不重复页面标题，不把所有元数据塞进一行。状态颜色不能是唯一线索，文字也要写清。

## 反例与正例

### ❌ 反例：内部术语泄露

> `runtime_resolve proxy_unavailable`

用户不知道影响、能不能重试、该找谁。

### ✅ 正例：界面可行动

> 服务暂时不可用，当前请求没有完成。
> [重试] [查看详情]

### ❌ 反例：空洞 CTA

> 立即体验，开启高效未来！

没有对象、动作和结果。

### ✅ 正例：具体 CTA

> 导入项目，开始查看部署结果
> [导入项目]

## 与流程机制的边界

- 权限、数据写入、路由、调度、发布和验收属于流程或系统机制；本 skill 只写界面看到的措辞和状态表达。
- 字号、留白、分页、配色、组件样式、动画和布局由设计/渲染规范负责，本 skill 不写数值。
- 平台语气与受众心智指向 `platform-voices`；本 skill 不重复平台运营规则。
- 触达 owner 的通道选择属于流程。界面通知文案只写内容，按使用方自己的路由规则投递。
- 汇报格式以 `task-reporting` 为准；`executive-briefing` 只叠加 `✅/⏸` 与拍板项。
- 停手/上报只认五类必停项：花钱、删生产数据、对外发布、凭据变更、项目方向。

## 自检清单

- [ ] 按钮是否写动作结果，而不是“确定/提交”？
- [ ] 标题是否说清当前对象或任务？
- [ ] 空态是否区分无数据、无结果、无权限和加载失败？
- [ ] 错误是否写影响、恢复动作和可查详情？
- [ ] 超长文本是否可读、可展开、不改变语义？
- [ ] 卡片是否按对象、状态、下一步组织？
- [ ] 是否删掉内部术语、错误码堆砌和无信息量口号？
- [ ] 是否没有混入字号、间距、路由或权限逻辑？
- [ ] 状态是否同时有文字线索，不只依赖颜色或图标？
- [ ] 是否按第一次使用界面的人身份通读过一遍？
