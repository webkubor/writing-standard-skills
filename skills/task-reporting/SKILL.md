# 任务回执与状态汇报

## 适用范围

适用于代码、文档、脚本、巡检、内容交付、长任务等工作的回执，也适用于周报中的单条进展。它管“怎么把事实写准”，不管任务状态如何流转、通知发到哪里、验收由谁批准。

统一格式只有一个：

```text
状态一行

## 已交付产物与 commit/分支

## 真实验证命令与输出证据

## 未决缺口或待拍板项
```

状态一行先写结论，再写范围或影响。三段都必须存在；没有内容的段落写明“无”或“本轮未产生”，不要用空白制造误会。

## 状态一行

按实际终态选择，不把过程当成终点：

- 成功：写“已完成”，并说清产物现在在哪里。
- 失败：写“未完成”，并说清失败点与是否可恢复。
- 阻塞：写“已阻塞”，并说清被什么挡住、需要什么决策。
- 无变化：写“本轮无变化”，说明检查范围与原因，不把空跑包装成完成。
- 周报条目：写清本周结果、数字和下一步；它是周报体裁，不冒充单次任务回执。

任务回执的行数不硬性限制，但状态必须能单独读懂。短改动可以只写状态一行，长交付必须补齐三段。

## 三段固定写法

### 已交付产物与 commit/分支

只写已经产生的对象、版本或位置：

- 文件、文档、构建产物、接口、界面或数据结果。
- 可追溯的提交号、分支或版本；没有提交就写“未产生 commit”。
- 多项目时按项目分组，不让读者从文件名猜归属。

不要把“已经提交”“已经合并”“已经部署”“业务已验收”写成同一个“完成”。它们分别需要各自的证据，见下文。

### 真实验证命令与输出证据

写实际执行过的命令、结果摘要和可查证入口。命令要能复现，输出要足以支撑状态：

```text
$ <命令>
<关键输出、退出码、数量或错误摘要>
```

证据优先级是真实输出、构建或测试报告、运行时读回、独立记录；截图或链接只能作为入口，不能单独证明所有阶段。没跑的命令不写成“已验证”，取不到的数据不写成成功。

### 未决缺口或待拍板项

把仍缺的材料、未覆盖的环境、失败项、限制和需要拍板的事项列出来。每项写清影响与下一步。没有就明确写“无”。

最终答案必须自包含：它是用户看到工作的第一眼，不接续中途进度更新。只保留用户需要的结果、产物、验证证据和未决缺口，不带入推理过程、工具调用、子 agent 指令或其他 agent 留下的简写、行话与文风；术语和细节以 `how-to-write` 的「原词说事，终稿自包含」门禁为准。

任务未完成且仍有授权范围内的下一步时，不要用“建议下一步”“计划如下”或常规选择题代替执行。先说明已采用的假设和决定，再把可验证、可恢复的下一步做完；只有范围发生重大变化、遇到过不去的坎、需要拍板或即将执行不可逆操作时才停下来问用户。拍板项仍按五类必停项判定：花钱、删生产数据、对外发布、凭据变更、项目方向。其余问题先完成可授权的修复、挂单或交接，不把普通执行困难升级成拍板项。

## 四种回执模板

### 成功回执

```text
✅ 已完成：<结果与用户可见变化>

## 已交付产物与 commit/分支
<产物、版本、提交号、分支>

## 真实验证命令与输出证据
<命令与关键输出>

## 未决缺口或待拍板项
无
```

### 无变化回执

```text
🟡 本轮无变化：<检查对象> 未发现需要处理的差异

## 已交付产物与 commit/分支
无（本轮未修改文件）

## 真实验证命令与输出证据
<检查命令、时间范围、结果摘要>

## 未决缺口或待拍板项
<未覆盖范围；无则写“无”>
```

### 失败回执

```text
❌ 未完成：<失败点与当前影响>

## 已交付产物与 commit/分支
<已完成部分；失败部分写明未产生什么>

## 真实验证命令与输出证据
<命令、退出码、错误原文或日志入口>

## 未决缺口或待拍板项
<可恢复动作或阻塞原因>
```

### 阻塞回执

```text
⏸ 已阻塞：<一句话卡点>

## 已交付产物与 commit/分支
<阻塞前已完成的对象>

## 真实验证命令与输出证据
<证明确实卡住的命令与输出>

## 未决缺口或待拍板项
仅限五类必停项时写拍板选项；否则写交接、补料或重试动作。
```

## 周报条目

周报是“本周重点 / AI 使用情况 / 问题与风险 / 下周计划”四章节中的一条，不改造成任务回执模板。每个条目写结果、证据和风险，不写流水账；OKR 条目另行按 KR、证据、周期组织。

## 反例与正例

### ❌ 反例：混报阶段

> 代码已合并，任务已完成，部署也好了，测试全绿。

这句话把提交、合并、部署和测试当成同一事实。若没有远端读回、构建记录和部署结果，读者无法知道哪一步真正完成。

### ✅ 正例：阶段分开

> ✅ 已完成：修复已在目标分支落地，测试环境已部署；业务验收尚未执行。
>
> 已交付产物与 commit/分支：`fix-result`，commit `abc123`，分支 `release/test`。
>
> 真实验证命令与输出证据：`npm test` 退出码 0；部署读回返回目标版本；业务验收清单尚未勾选。
>
> 未决缺口或待拍板项：业务验收未执行，影响是不能宣称线上可用。

### ❌ 反例：只有动作没有结果

> 已执行推送，详情见日志，应该没问题。

“执行”不是结果，推送回执也不能证明部署或验收。

### ✅ 正例：把证据写成结论

> ✅ 已完成：目标环境已运行新版本，版本读回为 `v2.5.0`。
>
> 真实验证命令与输出证据：`curl .../health` 返回 200，版本端点返回 `v2.5.0`，构建记录指向 commit `def456`。

## 与流程机制的边界

- 任务状态、Run 租约、分支策略、部署门禁、验收流程属于流程或项目规则；本 skill 只写回执措辞与证据怎么陈述。
- 触达 owner 的通道选择属于流程。本 skill 只写措辞，按使用方自己的路由规则投递，不在正文里写死路由。
- 汇报格式以 `task-reporting` 为准；`executive-briefing` 只叠加 `✅/⏸` 与拍板项。
- 停手条件只有四类：范围重大变化、过不去的坎、需要拍板、不可逆操作；其中五类必停项属于“需要拍板”。

## 自检清单

- [ ] 状态一行是否只声称证据支持的阶段？
- [ ] 已交付产物、提交或分支是否可定位？
- [ ] 是否列了真实命令、退出码或输出证据？
- [ ] 提交、合并、部署、业务验收是否分别写清？
- [ ] 无变化是否写明检查范围，而不是空泛说“正常”？
- [ ] 失败或阻塞是否保留错误原文、影响和下一步？
- [ ] 未决项是否与事实对应，没有把普通问题升级成拍板项？
- [ ] 终稿是否自包含，且没有带入推理过程、工具调用或子 agent 的简写行话？
- [ ] 授权范围内是否还有可执行的下一步，而非只留下计划、建议或执行说明？
- [ ] 周报条目是否保持周报体裁，没有冒充单次任务回执？
- [ ] 是否从第一次读这份回执的人角度通读过一遍？
