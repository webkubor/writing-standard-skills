# 人称、身份与对外口吻

## 适用范围

适用于公开内容、评论、回复、私信接待、CTA、署名和作者简介。它管“谁在说话、能代表谁、怎么回应”，不管账号授权、发布流程、平台算法、数据统计或通知路由。

## 人称与身份

- 正文默认用“我”，一篇内容中不要在“我”、第三人称和产品名之间来回切换。
- 作者栏、签名、系列入口可以使用公开账号名或作品名；正文叙述仍按同一人称。
- 不在对外文案里暴露私下称呼、协作角色、代笔关系、生成来源或内部执行者。
- 署名报告与个人发言分开：前者用客观陈述，后者才用第一人称。不能让署名人替执行过程认错。
- 不代表组织、客户或第三方做承诺；只能说自己能证明的事实和自己负责的动作。

## 评论与回复

按“承认事实 → 回应问题 → 留出回路”写，不把评论区当公告栏：

```text
这个现象我复现了，确实和页面显示不一致。
目前先给出可验证的下一步：<动作/入口>。
如果你手上的版本或数据不同，按你那边的判据继续核。
```

批评先接住事实，不急着辩解；不确定就写不确定。需要转给负责人时，写清依据和下一步，不替对方下结论。

## CTA

CTA 要自然、具体、可选：

```text
❌ 关注我，评论区回复“资料”才发
✅ 把你遇到的场景写在评论里，我们一起看
```

CTA 不用关注、点赞、转发、私信做条件交换，不制造稀缺或虚假承诺。资源、链接和下一步应直接可见；平台具体红线看 `platform-voices`。

## 反例与正例

### ❌ 反例：身份串台

> 我（产品名）觉得这个功能不错，另外某个助手帮我改过，大家关注我获取资料。

人称、公开身份、协作痕迹和条件式 CTA 混在一起，读者无法判断谁在承诺什么。

### ✅ 正例：边界清楚

> 我把这个功能跑了一遍，确实少了两个边界提示。复现步骤和结果放在下一条。
> 你遇到的是空数据还是权限不足？评论里说一下，我按同一条件再核。

### ❌ 反例：评论里替别人决定

> 这个肯定是后端的问题，让他们马上改。

没有证据，且把归因和责任推给个人。

### ✅ 正例：事实先行、留回路

> 请求确实返回 500，现象记录在这里。前端目前看不到服务端日志，建议先按这个入口核；如果你们的口径不同，以现场数据为准。

## 平台细则

小红书、X、Reddit、掘金、网易云、公众号等平台的受众心智、评论禁忌、标题钩子和平台红线看 `platform-voices`。本 skill 不复制平台清单，只提供通用的人称、身份和互动口吻。

## 与流程机制的边界

- 账号授权、身份矩阵、发布审批、平台 API、标签策略、数据归因和调度属于流程；本 skill 只写表达。
- 评论/回复的实际发送、编辑、删除和申诉按平台与项目规则执行。
- 触达 owner 的通道选择属于流程。对外 CTA 或回复只写措辞，按使用方自己的路由规则投递。
- 汇报格式以 `task-reporting` 为准；`executive-briefing` 只叠加 `✅/⏸` 与拍板项。
- 停手/上报只认五类必停项：花钱、删生产数据、对外发布、凭据变更、项目方向。

## 自检清单

- [ ] 正文人称是否统一，默认“我”或客观陈述？
- [ ] 公开账号名、作品名和私人称呼是否没有串台？
- [ ] 是否没有暴露内部执行者、代笔关系或未授权身份？
- [ ] 评论是否先承认可核事实，再回应和给出下一步？
- [ ] 不确定的地方是否明确说不确定？
- [ ] CTA 是否自然、具体、可选，不以关注/私信做交换？
- [ ] 平台细则是否只引用 `platform-voices`，没有复制第二套规则？
- [ ] 是否没有把账号授权、路由、审批写进表达规范？
- [ ] 是否把署名报告和第一人称发言分开？
- [ ] 是否以第一次读到这条内容的读者身份通读过一遍？
