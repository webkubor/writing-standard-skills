# 对上极简汇报与卡单拍板规范

给业务负责人（Owner、技术总监、业务决策者）汇报，和给同侧同事沟通是**两套完全相反的逻辑**：
- 对同侧同事要留余地、给台阶、归因于情境（`peer-facing-writing`）；
- **对业务负责人要极简、结论先行、不铺过程、直击代价**。

负责人最大的稀缺资源是**注意力和决策心智**。他们不需要知道你中间踩了多少坑、试了多少种方法——**他们要的是享受成果，或者在真正需要拍板的交叉路口做选择题。**

---

## 零、只允许存在的两种汇报形态

发给负责人的汇报，必须属于以下两种形态之一；**任何介于两者之间的“半成品（我正在做、我打算做、我想请示）”一律禁止发送**：

```
                    【发给负责人的两种合法形态】

  【形态一：✅ 已完成】
   1. 交付成果：做完了什么（业务价值 / 改动面）
   2. 落地指针：在哪能看到 / 在哪能用（URL、命令、Release 标签）
   3. 外部证明：怎么证明是真的做好了（测试全绿 / 监控指标 / 错误归零）

  【形态二：⏸ 仅剩拍板项】
   1. 事实背景：一句话说清卡在哪（仅限：花钱 / 不可逆 / 发版 / 凭据 / 战略方向）
   2. 互斥选项：选项 A 的收益与代价 vs 选项 B 的收益与代价
   3. 推荐立场：执行层的明确倾向与第一理由（不当两头堵的传声筒）
```

## 一、拍板项提问四步法（The Decision Request Formula）

当任务遇到无法自主闭环的阻塞、必须请负责人决断时，严禁发“要不要我做X”或长篇大论倒苦水，严格套用以下四步公式：

### 1. 背景只给一句事实
只讲与决策直接相关的客观数字或硬约束，不讲自己的心路历程。
- ❌ “今天排查了一下午，试了方案A不行，后来又去看了官方文档，发现第三方的接口好像有点变动……”
- ✅ “第三方接口上调单次调用价格至 ¥0.8，按当前并发日消耗将突破预算红线（¥400/天）。”

### 2. 为什么只有你能拍（权责锁定）
明确说明这件事为什么执行层不能擅作主张（必须属于以下五类必停项之一）：
`① 花钱/额度` · `② 删数据或不可逆操作` · `③ 对外发版` · `④ 凭据变更` · `⑤ 战略方向调整`。

### 3. 给出互斥选项与各自代价（不问开放大题）
把问题收敛为互斥的 2~3 个封闭选项，并**显式列出每个选项的代价与副作用**：
```markdown
- **选项 A（继续直连）**：业务稳定性 100%，但每月额度开销超支约 ¥6,000。
- **选项 B（降级为本地缓存 + 异步刷新）**：额度开销压降 90%，但首次查询将有 2 秒冷启动延迟。
```

### 4. 推荐选项与第一理由（带立场提问）
执行层必须有自己的专业倾向，不要做“两手一摊让领导选”的甩手掌柜：
```text
“执行层推荐【选项 B】。因为该业务对实时性不敏感，2 秒延迟对用户转化无实质影响，且能守住成本红线。”
```

## 二、正反案例对比

### ❌ 假人倒苦水与甩锅请示体
> 恩博，跟你同步一下今天的情况。今天本来打算把数据迁移做完的，但是搞了一天发现这个老数据库里面有些表字段对不上，而且网络好像也有点抖动，我重试了好多次。另外就是那个 Cloudflare 的 Token 权限有点问题，报了 10000 错误，我不太确定要不要去改它的策略，还是说我们重新建一个新 Token？如果建新 Token 的话可能要你提供一下管理员密码。你觉得我们接下来怎么处理比较好呢？要不要我先去看看别的问题？

### ✅ 工业级极简交付与拍板体
> **一、✅ 已完成交付**  
> 1. 主数据库 25 张表全量完成 Supabase 迁移与数据校验，旧库已执行安全删除；  
> 2. `cs db` 命令行工具完成收敛，仅保留博客内容库；  
> 3. 门禁验证全量通过（5 表唯一登记），已发版 `v4.3.0` 并完成全节点推送。  
> 
> **二、⏸ 仅剩拍板项：Cloudflare Token 权限收敛**  
> - **事实**：`cs domain` 报错 10000 的根因为当前凭据缺少 `Zone:DNS:Read` 权限，需在控制台扩权。  
> - **选项 A**：由你在 Dashboard 为既有 `cf-api-token` 勾选该权限（耗时 1 分钟，全流程无需凭据交接）；  
> - **选项 B**：由执行层通过 Chrome 自动化直接生成全新 master token（需你授权唤起 Chrome 会话）。  
> - **推荐**：推荐【选项 A】，凭据生命周期最可控，风险为零。

## 三、📋 Executive Briefing 扣分清单（Deduction Rubric）

任何面向负责人的汇报与进度同步前逐条核验，**命中任何一项扣 25 分（满分 100，低于 75 分重写）**：

| 违规维度 | 扣分项（Anti-pattern） | 扣分 | 为什么致命 | 修正方案 |
|---|---|:---:|---|---|
| **过程冗余** | **把操作过程当成果，汇报大量中途排查流水账** | -25 | 极度消耗负责人阅读心智，让核心结果被信息噪点淹没。 | 过程进 Commit、单据和 Retro，汇报首行只给「结论与交付成果」。 |
| **开放请示** | **向负责人提问操作级问题（“怎么配/要不要我做/下一步干啥”）** | -25 | 把负责人降级为日常操作员，本质是执行层在逃避专业责任。 | 操作问题内部自答自闭环，只将带有实质代价的互斥选项上桌。 |
| **半成品汇报** | **汇报“我正在看/我打算做/稍后给您看”等在途状态** | -25 | 在途状态属于执行者的内部事务，不是负责人需要消费的资产。 | 做完且具备外部可查证据再汇报；卡住则直接转为【形态二：拍板项】。 |
| **立场缺失** | **提了两个选项但两手一摊不给推荐与理由（“领导您看呢”）** | -25 | 逼迫负责人重新下钻业务细节做调研，失去了助手的中枢价值。 | 必须明确给出执行层推荐项（“推荐 A，因为……”），供负责人一键定夺。 |
