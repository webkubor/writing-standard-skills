# 单据与协作记录文案

## 适用范围

适用于 issue、MR/PR 描述、依赖单、问题复现单、交接单和需要多人执行的协作记录。它管单据怎么写得可接、可验、可追溯，不负责项目状态字段、权限、看板、通知路由或审批流程。

## 标题

```text
[项目名] 一句话说清问题或目标（含可判断的终点）
```

### ❌ 反例

```text
修一下图床
```

标题没有项目、现象或终点，接手者无法判断归属与完成条件。

### ✅ 正例

```text
[示例项目] 图床路由表漂移：清理错路径并恢复 11→7 条映射
```

另一个人只看标题，应该能判断“这事是不是我的、什么现象算做完”。

## 正文骨架

### 背景

写清为什么现在提这张单，避免“已知问题”这类空话。需要业务决策时再补用户场景和业务后果。

### 现象

放报错原文、日志行、请求/响应、数据对比和复现结果。现象必须可核对，不能只写“有问题”。错误来自主机、网关还是业务代码也要区分。

### 复现步骤

按第一次接手的人能照做的顺序写：

```text
1 环境/版本：<可查证入口>
2 前置条件：<必要数据、配置或状态>
3 操作：<最小步骤>
4 实际结果：<原文或截图入口>
5 预期结果：<判据>
6 复现频率：<稳定/偶发/仅特定数据>
```

步骤越少越好，但不能省掉关键前置条件。

### 验收标准

写成 checkbox，使用可执行判据：

```markdown
- [ ] `<命令>` 返回 `<结果>`，退出码为 `<code>`
- [ ] `<页面/接口>` 在 `<条件>` 下显示 `<结果>`
- [ ] 回归测试 `<范围>` 通过
- [ ] 破坏性变更已给出迁移步骤（如适用）
```

“看着对”“体验正常”不是验收标准。构建绿、接口 200 或截图存在，也不能单独证明功能正确。

### 边界

写清不做什么、谁执行、谁验收、依赖什么。把不在对方范围内的部分明确划走，减少误会。执行方和验收方不要写成同一个人，除非项目规则另有说明。

### Refs

引用统一写成可定位的短链或标识：

```markdown
Refs: issue #123
Refs: MR !456
Refs: commit abc123
Refs: PRD §3.2
```

`Refs` 是查证入口，不是结果证据。若引用失效，正文仍要保留关键原文和判据，不让单据只剩断链。

## 依赖单

依赖单只写对方需要知道的最小上下文：

```text
依赖对象：<接口、资源、决定或任务>
需要什么：<具体输入或动作>
截止/影响：<不做会影响什么>
当前证据：<命令、记录或复现入口>
可逆性：<是否需要拍板；仅五类必停项才升级>
```

## MR/PR 描述

```text
结论：<改完后的行为变化>
改动面：<文件、模块或接口范围>
验证：<命令、测试、截图或读回证据>
风险与回滚：<影响面、失败时怎么退>
Refs：<issue、设计或需求入口>
```

提交、合并、部署、业务验收分开写。MR 通过不等于部署完成，部署完成不等于业务验收通过。

## 反例与正例

### ❌ 反例：只贴报错

> 500 了，麻烦查一下。

没有版本、请求、数据、预期结果，接手者只能猜。

### ✅ 正例：最小可复现

> **现象**：在版本 `v2.5.0`、空数据状态下打开列表页，接口返回 500，响应体为 `...`。
>
> **复现**：`npm run dev` → 打开 `/list` → 点击刷新；稳定复现。
>
> **验收**：空数据状态显示空态文案，接口返回 200；`npm test -- list` 通过。
>
> **边界**：不改分页接口契约，不处理历史数据。

## 与流程机制的边界

- issue 状态、标签、权限、分支保护、合并规则、审批和通知属于项目流程；本 skill 只管单据措辞和证据表达。
- 复现、验收和 Refs 是单据内容；状态流转和责任人变更按项目流程执行。
- 触达 owner 的通道选择属于流程。本 skill 只写文字，按使用方自己的路由规则通知。
- 汇报格式以 `task-reporting` 为准；`executive-briefing` 只叠加 `✅/⏸` 与拍板项。
- 停手/上报只认五类必停项：花钱、删生产数据、对外发布、凭据变更、项目方向。

## 自检清单

- [ ] 标题包含项目、问题和可判断终点吗？
- [ ] 背景、现象、复现、验收、边界是否齐全？
- [ ] 现象是否保留原文、版本、环境和复现频率？
- [ ] 复现步骤是否由第一次接手的人可独立执行？
- [ ] 验收 checkbox 是否有命令、结果、退出码或界面判据？
- [ ] `Refs` 是否能定位到 issue、MR、PR、commit 或需求？
- [ ] 依赖单是否写清输入、截止、影响和证据？
- [ ] MR/PR 是否分开写改动、验证、风险和回滚？
- [ ] 是否把提交、合并、部署、业务验收混成一个状态？
- [ ] 是否删除了与判断无关的私人信息、路径和内部代号？
